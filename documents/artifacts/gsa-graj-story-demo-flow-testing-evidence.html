1 · The Story

The Problem We Solved

In a federal healthcare program office, an analyst gets an email from a program manager at 9 a.m.: "Can you pull me the total treatment cost by city for 2024, and flag any patients whose data should be redacted before sharing?"

Under the old workflow, that request goes into a ticketing queue, waits two days for a data engineer, produces a raw CSV with no PII scrubbing, and arrives the following week — too late for the morning brief.

With GSA GRAJ, the program manager types that same question directly into the AI chat, hits send, and has a live-sourced, PII-redacted, ranked result in under 20 seconds. No ticket. No SQL. No wait.

Four Pain Points We Targeted

🕐

Slow turnaround

Ad-hoc analytics routed through ticketing queues arrive days or weeks late, missing decision windows.

🔓

PII exposure risk

Staff export raw tables and share them without systematic redaction, risking HIPAA violations.

📊

Excel dependency

Operational data lives in spreadsheets that never reach the central database, creating shadow datasets.

📉

No self-serve charts

Tabular SQL outputs require a separate BI tool and additional technical expertise to visualise.

How GSA GRAJ Solves Each One

Instant analytics

Natural-language → live PostgreSQL query → grounded answer in seconds, via IBM watsonx Orchestrate and FastMCP.

Automatic PII redaction

gsa_graj_viz_redact_pii scans 20+ column types and cell-level regex patterns before any data is displayed.

Chat-attached Excel loader

Attach any .xlsx in the chat window. The agent loads it into PostgreSQL instantly — append or replace mode.

Conversational charts

One sentence creates a bar, line, scatter, histogram, heatmap, or table — rendered as markdown and exportable as CSV.

2 · How It Works — Natural Language to Live Data

Every user message passes through a five-step pipeline. The agent never answers from memory — if a tool hasn't been called, no data is shown.

💬
1. User speaks
Plain English in the wxO chat window
🧠
2. LLM interprets
groq/openai/gpt-oss-120b maps intent to the right tool + parameters
🔧
3. MCP tool fires
FastMCP server executes SQL or logic against live PostgreSQL
🛡️
4. PII guard
redact_pii runs before any row-level data is returned to the user
✅
5. Grounded reply
Tool output + SQL shown verbatim — no hallucination possible

3 · Effective Demo Flow — Step-by-Step Script

Run these seven demonstrations in order. Each one builds on the previous and shows a distinct capability. Estimated time: 12–15 minutes.

1
Schema Discovery — "What data do we have?"
"What tables exist in the database and what columns does operational_tbl have?"
→ gsa_graj_connect_sl_db() → returns table list + 15 column definitions
✓ Shows full schema: patient_id, name, gender, dob, age_at_admission, city, blood_group, date_admitted, health_issue, ward, attending_doctor, discharge_date, length_of_stay_days, discharge_status, treatment_cost_usd

What to highlight: The agent discovers the live schema in real time — no hardcoded knowledge.

2
Aggregation + Ranking — "Top cities by cost"
"Which five cities have the highest total treatment cost?"
→ gsa_graj_query_operational_tbl(aggregate_function="SUM", aggregate_column="treatment_cost_usd", group_by_columns="city", order_by="result DESC", limit=5)
✓ Returns ranked table with city names and dollar totals. SQL shown verbatim.

What to highlight: "Top N" ranking in plain English maps automatically to ORDER BY + LIMIT — no SQL written by user.

3
Date Granularity — "Trend across all years"
"What is the total treatment cost for each admission year across all years?"
→ gsa_graj_query_operational_tbl(aggregate_function="SUM", aggregate_column="treatment_cost_usd", group_by_columns="date_admitted", date_granularity="year", order_by="year_date_admitted ASC")
✓ Returns all 5 years (2022–2026) in one call. 2026 partial — data runs to April only.

What to highlight: This was a known regression (agent previously refused with "too many calls"). Fixed with date_granularity="year" parameter — single tool call returns all years at once.

4
PII Redaction — "Show data safely"
"Show me the first 10 rows from operational_tbl but redact any personally identifiable information before displaying."
→ gsa_graj_read_from_sl(table_name="operational_tbl", limit=10)
→ gsa_graj_viz_redact_pii(query_result_json=..., scan_values=True)
✓ name → ***REDACTED*** · patient_id → ***REDACTED*** · dob → ***REDACTED*** · attending_doctor → ***REDACTED***. Non-PII columns (city, ward, cost) shown as-is.

What to highlight: Two-level detection: column-name matching (20+ PII field names) + cell-value regex (email, phone, SSN, credit card, IP, date patterns). Automatic, no user configuration needed.

5
Excel Upload — "Load a spreadsheet"
[Attach patients.xlsx in chat window] "Load this file into a new table called uploaded_patients, replacing any existing rows."
→ gsa_graj_load_excel_to_postgres(excel_file=WXOFile, table_name="uploaded_patients", if_exists="replace")
✓ "Successfully inserted N row(s) into table 'uploaded_patients'. Mode: replace."

What to highlight: File attached in chat — no S3, no API, no staging area. Auto-creates the table with TEXT columns, normalises headers to lowercase_underscore. Append mode also available.

6
Visualisation Agent — "Draw a chart"
"Show monthly admissions trend for 2024 as a line chart." (in gsa_graj_viz_agent)
→ gsa_graj_viz_inspect_schema()
→ gsa_graj_viz_preview_query(sql="SELECT DATE_TRUNC('month', date_admitted)...")
→ gsa_graj_viz_run_query(sql=..., chart_type="line", x_column="month", y_column="count")
✓ Markdown line chart rendered. SQL block shown. Row count disclosed. CSV export offered.

What to highlight: Schema → validate → execute → render in one conversational turn. Chart type inferred from "trend" → line. User never sees SQL unless they want to.

7
Evaluation Agent — "Prove it works"
"Run the aggregate tag examples and show me correctness and scope scores."
→ gsa_graj_eval_get_dataset(tag_filter="aggregate") → 8 examples
→ gsa_graj_agent (collaborator) for each question
→ gsa_graj_eval_correctness + gsa_graj_eval_scope per response
✓ Results table with CORRECT / IN-SCOPE scores. Summary: correctness %, scope %.

What to highlight: The system benchmarks itself — the eval agent calls the agent under test, scores responses with two independent judges, and produces a reproducible results table.

5 · Bugs Found During Testing & How They Were Fixed

Testing is not just about passing scores — it's about discovering failure modes and proving they were fixed. Two significant bugs were caught and resolved:

Bug 1 — Agent refused yearly aggregation: "would require too many calls"
Root cause: (1) Duplicate tool number "── 6." in agent instructions confused the LLM's routing logic — it couldn't reliably distinguish the Excel tool from the analytics tool. (2) No example of date_granularity="year" existed in the tool-call mapping section. (3) No explicit rule banning the refusal pattern.
Fix applied: Renumbered tools (Excel=6, analytics=7). Added a yearly aggregation example to the MAPPING section. Added two ABSOLUTE RULES at the top of instructions banning any refusal of date-grouping requests and the "too many calls" excuse. Verified with Example 13 live run above.
Bug 2 — PII redaction tool unavailable after viz toolkit rebuild
Root cause: gsa_graj_viz_redact_pii was added to toolkits/gsa_graj_viz/server.py but the live Code Engine container was not updated. The toolkit registered in WXO still pointed to the old image, which did not expose the new tool.
Fix applied: Rebuilt the gsa_graj_viz Docker image, pushed to ICR (ca.icr.io/gsa-graj-wxo/gsa-graj-viz:latest), ran ibmcloud ce app update, then removed and re-imported the toolkit into watsonx Orchestrate. Verified via orchestrate toolkits list and a live PII redaction test.

6 · PII Redaction — Detailed Evidence

PII protection is a first-class capability, not an afterthought. The gsa_graj_viz_redact_pii tool is called by both agents before displaying any row-level data, and it operates at two independent detection levels.

Level 1 — Column Name Matching (20+ patterns)

nameemailphone dobssnpatient_id addressgenderattending_doctor salarynational_idiban passportlicenserace ethnicitybiometricip_address mac_address

Level 2 — Cell Value Regex Scanning

email addressesphone numbers SSN (XXX-XX-XXXX)credit cards IPv4 addressesISO dates (DOB) UK NHS numbersUK postcodes US ZIP codes

Masked value: ***REDACTED***  |  scan_values=True (default) enables Level 2  |  sensitive_columns param forces extra columns beyond defaults.

What a redacted output looks like

Before redaction:
  {"patient_id": "P-10042", "name": "Jane Smith", "dob": "1985-03-14",
   "attending_doctor": "Dr. A. Chen", "city": "Toronto", "treatment_cost_usd": 4820.50}

After gsa_graj_viz_redact_pii:
  {"patient_id": "***REDACTED***", "name": "***REDACTED***", "dob": "***REDACTED***",
   "attending_doctor": "***REDACTED***", "city": "Toronto", "treatment_cost_usd": 4820.50}

Non-PII columns (city, treatment_cost_usd) pass through unchanged. PII detection is automatic — users do not need to specify which columns to mask.
